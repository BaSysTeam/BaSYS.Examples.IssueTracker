# Архитектура метаданных BaSYS

## 1. Архитектурные решения

1. `issue` и `development_task` проектируются как метаобъекты вида `operation`. Операция дает нумерацию и дату, ссылочный тип, вложения, историю, табличные части, формы и стандартный ввод на основании.
2. `release`, `person` и `tag` проектируются как справочники (`catalog`). Они являются ссылочными классификаторами и не нуждаются в проведении по регистрам.
3. Переписка хранится в обычном регистре `discussion_message` (`register`), без вложений и собственной программируемой формы.
4. Фиксированные наборы значений моделируются перечислениями (`enum`).
5. Записи регистров (`records`), проведение операций, workflows и программируемые Vue-формы для MVP не используются.
6. Все новые технические имена — английские `snake_case`, не длиннее 30 символов для метаобъектов.

## 2. Состав метаданных

| Реализовано | Вид BaSYS | Техническое имя | Заголовок | Назначение |
|---|---|---|---|---|
| [ ] | `operation` | `issue` | Обращение | Входящий запрос, идея или ТЗ |
| [ ] | `operation` | `development_task` | Задача разработки | Единица планирования и выполнения |
| [ ] | `catalog` | `release` | Релиз | Версия продукта и ее описание |
| [ ] | `catalog` | `person` | Физическое лицо | Автор и исполнитель |
| [ ] | `catalog` | `tag` | Тег | Гибкая классификация обращений и задач |
| [ ] | `register` | `discussion_message` | Сообщение обсуждения | Переписка по обращениям |
| [x] | `enum` | `issue_type` | Тип обращения | Ошибка, предложение, идея, вопрос, ТЗ |
| [x] | `enum` | `issue_status` | Статус обращения | Жизненный цикл обращения |
| [x] | `enum` | `task_status` | Статус задачи | Жизненный цикл задачи |
| [x] | `enum` | `release_status` | Статус релиза | Жизненный цикл релиза |
| [x] | `enum` | `importance` | Важность | Общая шкала обращения и задачи |
| [x] | `enum` | `urgency` | Срочность | Скорость реакции на обращение |
| [x] | `enum` | `primevue_color` | Цвет PrimeVue | Общий набор семантических цветов для оформления |
| [ ] | `menu` | `main` | Основное меню | Навигация по системе |

UID в архитектурном документе не фиксируются. Они должны быть сгенерированы непосредственно при создании метаданных.

## 3. Операция `issue`

### 3.1. Заголовок

Помимо стандартных колонок операции (`number`, `date`, `is_deleted`, `is_files` и служебной колонки проведения) проектируются поля:

| Поле | Заголовок | Тип | Обязательное | Назначение |
|---|---|---|---|---|
| `title` | Заголовок | String | да | Краткое содержание обращения |
| `issue_type` | Тип | `enum.issue_type` | да | Ошибка, предложение, идея, вопрос или ТЗ |
| `status` | Статус | `enum.issue_status` | да | Текущий статус, по умолчанию «Новое» |
| `author` | Автор | `catalog.person` | да | Инициатор обращения |
| `responsible` | Исполнитель | `catalog.person` | да | Ответственное физическое лицо |
| `importance` | Важность | `enum.importance` | да | По умолчанию «Обычная» |
| `urgency` | Срочность | `enum.urgency` | да | По умолчанию «Обычно» |
| `description` | Описание | String, многострочный | да | Полное описание, допускается Markdown |
| `source_url` | Ссылка на источник | String | нет | Ссылка на исходное ТЗ, обсуждение или стенд |

Служебная возможность проведения операции не используется: `recordsSettings` и `recordsSources` остаются пустыми, а стандартное поле проведения скрывается из прикладных форм.

### 3.2. Табличная часть `tags`

| Поле | Заголовок | Тип | Обязательное |
|---|---|---|---|
| `tag` | Тег | `catalog.tag` | да |

Для пары «обращение + тег» не допускаются дублирующиеся строки.

### 3.3. Связанные данные

В карточке обращения размещаются два `TableView`:

- `tasks` — задачи `operation.development_task`, отфильтрованные по текущему обращению;
- `messages` — строки `register.discussion_message`, отфильтрованные по текущему обращению и отсортированные по дате.

Файлы открываются стандартной командой `standard.open_files`. Задача создается стандартной командой `standard.create_from`.

## 4. Операция `development_task`

### 4.1. Заголовок

| Поле | Заголовок | Тип | Обязательное | Назначение |
|---|---|---|---|---|
| `issue` | Обращение | `operation.issue` | да | Единственное основание задачи |
| `title` | Заголовок | String | да | Краткое название работы |
| `status` | Статус | `enum.task_status` | да | По умолчанию «Запланирована» |
| `author` | Автор | `catalog.person` | да | Автор постановки |
| `responsible` | Исполнитель | `catalog.person` | да | Единственный исполнитель |
| `importance` | Важность | `enum.importance` | да | Одновременно приоритет задачи |
| `description` | Описание | String, многострочный | да | Содержание работы |
| `planned_date` | Плановая дата | DateTime | нет | Ожидаемая дата завершения |
| `estimate_hours` | Оценка, ч | Decimal | нет | Плановая оценка в часах без учета факта |
| `release` | Релиз | `catalog.release` | нет | Релиз, в который включена задача |

### 4.2. Табличная часть `acceptance_criteria`

| Поле | Заголовок | Тип | Обязательное | Назначение |
|---|---|---|---|---|
| `description` | Критерий приемки | String | да | Отдельное проверяемое условие приемки задачи |
| `is_completed` | Выполнено | Boolean | да | Флажок выполнения критерия, по умолчанию снят |

Каждый критерий приемки хранится отдельной строкой, а `is_completed` отображается на форме флажком. Табличная часть необязательна, но если в ней есть строки, перевод задачи в статус «Выполнена» допускается только при установленных флажках во всех строках. Такая структура позволяет проверять готовность задачи по данным табличной части без разбора Markdown.

### 4.3. Табличная часть `tags`

Состав совпадает с табличной частью `tags` обращения. Совпадающие технические имена общих полей и таблиц облегчают перенос данных при вводе на основании.

### 4.4. Ввод на основании

Целевой сценарий:

1. Пользователь сохраняет обращение.
2. Выполняет «Создать на основании» и выбирает `development_task`.
3. В новую задачу переносятся общие данные: заголовок, автор, исполнитель, важность, описание и теги.
4. Поле `issue` заполняется ссылкой на исходное обращение.
5. Статус задачи устанавливается в «Запланирована»; релиз, плановая дата, оценка и строки критериев приемки заполняются при декомпозиции.

При реализации следует настроить очистку полей, которые не должны наследоваться при вводе на основании, через `autoClearMethod`. Если стандартное сопоставление BaSYS не заполняет обратную ссылку `issue`, необходимо настроить ее в механизме ввода на основании; отдельную универсальную сущность связи создавать не следует.

Как и для обращения, проведение по регистрам не используется, а файлы доступны стандартным механизмом вложений.

## 5. Справочник `release`

Используются стандартные поля справочника `id`, `title`, `is_deleted`; возможность файлов на форме не выводится.

| Поле | Заголовок | Тип | Обязательное |
|---|---|---|---|
| `status` | Статус | `enum.release_status` | да |
| `planned_date` | Плановая дата публикации | DateTime | нет |
| `published_at` | Дата публикации | DateTime | нет, обязательна по бизнес-правилу для опубликованного релиза |
| `description` | Описание изменений | String, многострочный | нет |

`title` содержит номер или человекочитаемое название версии, например `2026.08` или `1.4.0`.

В карточке релиза размещается `TableView` `tasks` с источником `operation.development_task` и фильтром `release = текущий релиз`. Задачи не копируются в табличную часть релиза: владельцем связи остается задача.

## 6. Справочник `person`

| Поле | Заголовок | Тип | Обязательное | Назначение |
|---|---|---|---|---|
| `title` | Заголовок | String | да | ФИО, вычисляемое формулой из фамилии, имени и отчества |
| `last_name` | Фамилия | String | да | Фамилия физического лица |
| `first_name` | Имя | String | да | Имя физического лица |
| `middle_name` | Отчество | String | нет | Отчество физического лица |
| `email` | Email | String | нет | Адрес электронной почты |

`title` является хранимой стандартной колонкой справочника и заполняется формулой, которая объединяет `last_name`, `first_name` и `middle_name` через пробел. Пустое отчество не должно приводить к лишнему пробелу в ФИО. Справочник предотвращает свободный ввод имен и обеспечивает ссылочные поля автора и исполнителя.

## 7. Справочник `tag`

| Поле | Заголовок | Тип | Обязательное |
|---|---|---|---|
| `title` | Тег | String | да |
| `color` | Цвет | `enum.primevue_color` | нет |

Название тега должно быть уникальным по смыслу. Цвет является необязательным оформительским атрибутом и не участвует в бизнес-логике. Во всех прикладных метаобъектах поля семантического цвета должны ссылаться на `enum.primevue_color`, а не хранить произвольную строку.

## 8. Регистр `discussion_message`

| Поле | Заголовок | Тип | Обязательное |
|---|---|---|---|
| `issue` | Обращение | `operation.issue` | да |
| `created_at` | Дата и время | DateTime | да |
| `author` | Автор | `catalog.person` | да |
| `text` | Сообщение | String, многострочный | да |

Регистр не поддерживает вложения по возможностям вида и по требованиям продукта. Сообщения сортируются по `created_at`. Для быстрого чтения переписки нужен индекс, начинающийся с `issue` и включающий дату сообщения.

## 9. Перечисления

### `issue_type`

| `name` | Заголовок |
|---|---|
| `bug` | Ошибка |
| `proposal` | Предложение |
| `idea` | Идея |
| `question` | Вопрос |
| `specification` | ТЗ |

### `issue_status`

`new` — Новое; `review` — На рассмотрении; `accepted` — Принято; `in_progress` — В работе; `done` — Выполнено; `rejected` — Отклонено; `duplicate` — Дубликат.

### `task_status`

`planned` — Запланирована; `in_progress` — В работе; `review` — На проверке; `done` — Выполнена; `canceled` — Отменена.

### `release_status`

`planned` — Планируется; `preparing` — Готовится; `published` — Опубликован.

### `importance`

`low` — Низкая; `normal` — Обычная; `high` — Высокая; `critical` — Критическая.

### `urgency`

`not_urgent` — Не срочно; `normal` — Обычно; `urgent` — Срочно; `immediate` — Немедленно.

### `primevue_color`

`primary` — Основной; `secondary` — Вторичный; `success` — Успех; `info` — Информация; `warning` — Предупреждение; `danger` — Опасность; `contrast` — Контрастный.

Значения соответствуют семантическим цветам (`severity`) компонентов PrimeVue. Перечисление используется во всех прикладных полях цвета, чтобы оформление оставалось согласованным с текущей темой интерфейса.

## 10. Формы

Для MVP достаточно форм-конструкторов и штатных автоформ. Программируемые `.vue`-формы не нужны.

| Объект | Список | Карточка |
|---|---|---|
| Обращение | Стандартный список с фильтрами | Форма-конструктор: реквизиты, описание, теги, задачи, переписка, файлы, ввод на основании |
| Задача | Стандартный список с фильтрами | Форма-конструктор или автоформа: реквизиты, описание, критерии приемки с флажками, теги, файлы |
| Релиз | Стандартный список | Форма-конструктор: реквизиты, описание и `TableView` задач |
| Физическое лицо | Автоформа | Автоформа |
| Тег | Автоформа | Автоформа |
| Сообщение | Стандартный список регистра | Штатная форма строки регистра; основной вход — из карточки обращения |

Формы должны использовать стандартные команды сохранения, возврата, файлов и ввода на основании. Специализированные клиентские команды добавляются только если штатный сценарий не позволяет предзаполнить обращение в новом сообщении или задаче.

## 11. Списки и backlog

В первой версии не создаются `data_view`, Kanban или отдельный метаобъект backlog. Используются стандартные списки и фильтры:

- обращения: тип, статус, автор, исполнитель, важность, срочность, дата;
- задачи: статус, автор, исполнитель, важность, обращение, релиз, плановая дата;
- релизы: статус и даты публикации.

Если практика покажет, что ручных фильтров недостаточно, следующим расширением может стать одна панель данных `data_view.backlog`; это не меняет модель хранения.

## 12. Меню

Минимальное основное меню:

```text
Разработка
├── Обращения
├── Задачи
└── Релизы

Классификаторы
├── Физические лица
└── Теги
```

Перечисления не выводятся как пользовательские разделы меню. Регистр сообщений доступен преимущественно из карточки обращения.

## 13. Права и аудит

- Для всех прикладных метаобъектов команда получает полные доступные права.
- Ролевая сегментация данных в MVP отсутствует.
- Для операций и справочников сохраняется штатная история BaSYS.
- Реальные учетные данные и локальные параметры подключения не являются частью метаданных.

## 14. Рекомендуемая последовательность будущей реализации

1. Создать перечисления.
2. Создать справочники физических лиц, тегов и релизов.
3. Создать операцию обращения с табличной частью тегов и вложениями.
4. Создать операцию задачи, ссылку на обращение и релиз, табличные части критериев приемки и тегов.
5. Настроить ввод задачи на основании обращения.
6. Создать регистр сообщений и индекс переписки.
7. Создать минимальные формы-конструкторы с `TableView` связанных данных.
8. Создать меню.
9. Проверить типовой сценарий «ТЗ → несколько задач → релиз» и сценарий «вопрос → ответ без задачи».

На каждом шаге фактические UID и `dataTypeUid` должны браться из системных файлов BaSYS и созданных ранее ссылочных метаобъектов; значения не следует придумывать заранее в требованиях.
